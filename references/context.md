# Context selection and reuse

Read when maintaining routing, handoffs or caching; ordinary tasks use their skill's selected path.

| Context | Reuse boundary | Invalidate/reload |
| --- | --- | --- |
| Shared guidance | Canonical file + content revision + selected role | Changed source, role, task scope or lost context |
| Consumer constraints | Above + consumer root + applicable ancestor/nested rules | Workspace/scope/instruction changes; never borrow another project's authority |
| Check evidence | Exact checked inputs, command and environment | Relevant changes, failure or missing evidence |
| Catalog metadata | Existing runtime/config fingerprint | Incompatibility blocks; never authorizes discovery |
| User authorization | Recorded decision + consumer/action scope | Scope changes; never expand authority or re-ask for still-valid authorization |
| Account telemetry | Dated evidence only | Required live admission/claim remains fresh; never infer available capacity |

Reuse material already present; read only changed/newly applicable slices. After compaction retain source pointers and bounded verified progress, then rehydrate missing applicable contracts. Never drop required rules because a cache entry once existed. No credentials, application data or full transcripts in a shared cache.

Handoff order: execution contract/report schema → sorted selected consumer instructions → sorted selected task references → task plan. Emit a selected file once by filesystem identity, including aliases across groups; distinct files retain their own constraints. Supervisor/setup/catalog/account documents stay outside executor prompts. Stable-prefix reuse depends on actual provider behavior; never add irrelevant context, assume cache hits or discount budgets for them. Host communication/tool limits prevail.
